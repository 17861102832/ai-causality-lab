# 第一部分：AI 编程工具使用与工程方法论

想把 AI 编程工具真正用出效率，关键不在于"哪个模型分高"，而在于搞清工具的命名脉络与模式差异、避开一串可复现的坑、学会把上下文与规则喂饱、并把提示词与工作流沉淀成可复用的方法——本部分把「TRAE 交流群｜游戏」两年里群友亲测的工具用法、排障经验与工程范式系统整理成可上手的操作手册。

## 1.1 TRAE 工具全貌：命名脉络、模式差异与核心机制

### 1.1.2 SOLO 独立版：不再依附编辑器

SOLO 从"IDE 里的一个模式"升级为独立产品，是使用方式上的一次大变化：

> `[2026-04-09] 漫川`：这次 TRAE 全新上线的独立 Solo 和之前 IDE 里的版本完全不同，它不再依附编辑器，是独立的桌面/网页端工具，在保留原有代码能力的基础上新增了 MTC 全场景模式，能直接处理文档、数据分析等非代码任务，支持多任务并行和云端同步。

配套的落地节点：`[2026-05-05 13:28]` 耿家威「SOLO Windows 客户端出来了！！」；`[2026-05-05 11:39]` 用户456741「trae solo 增加了一个互动空间的 skill」。移动端获取方式：`[2026-05-05 11:25-11:27]` 耿家威「商店里搜索 trae」，AI发明家补充「国际版要有谷歌商店」「国内版直接搜索 trae 就行」。IDE 与 SOLO 的相互切换：`[2026-05-14 08:29]` 用户815023「点那个 ide 切换模式，可以切换到 solo 模式」。

### 1.1.3 模式差异：goal / IDE / Work / MTC

**goal 模式**并未下架，只是入口藏得深：

### 1.1.7 Skill 机制：本质是"按需加载的提示语"

> `[2026-01-09] 刘金良`：skill 说白了，也是提示语，之所以单独拿出来，目的是让 AI 在需要的时候加载，你以 `#文件` 的形式，只是让文件立马加载。

## 1.2 TRAE 常见问题与排障手册

### 1.2.1 官方答疑 VOL.5：代码补全问题解析大全

`[2025-11-28] 杜昔月`（官方）发布的高频问答，是本部分最可直接照搬的排障清单：

| 现象 | 原因 | 解法 |
|---|---|---|
| **补全速度慢** | 插件导致 LSP 冲突 | 先禁用所有插件，重启确认是否恢复；部分插件会冲突，如 `Vue-Official` 建议退回 **1.8.27** |
| **补全消失** | 网络延迟/超时，或代理（梯子）拦截 | 先检测网络；若必须连梯子，把 `trae-api-sg.mchost.guru` 与 `trae-api-us.mchost.guru` 纳入**不转发规则** |
| **补全出现提示音** | 开启了无障碍模式（如从其他 IDE 导入配置时带入） | 将 `Accessibility Support` 配置改为 `off` 或 `auto` |
| **cue 补全快捷键与 IDE 自带补全冲突** | 二者同时触发，难以彻底解决 | 用**不同快捷键规避**：`Enter` 采纳 IDE 自带补全，`Tab` 采纳 cue 补全 |
| **没有 Autoimport / rename** | LSP 类型检查未开启 | `Cmd+Shift+P` → 输入 settings → `Open User Settings` → 至少开启 `basic` 及以上类型检查；可在类名/函数名右键 `Go to References` 验证（初始化需一段时间） |

## 1.4 上下文工程与规则驱动开发

### 1.4.1 6A + 5S 规则：社区最完整的"规则驱动"范本

`[2025-10-28 22:27]` 庄子村 给出把 AI 约束成"按流程推进"的两套规则，是本群传播最广的规则工程实践。使用方式：Project Rules 页签粘贴 6A 全文，User Rules 页签粘贴 5S 全文，新建项目时输入激活口令 `6A-start`。

**project_rules.md ── 6A 工作流（项目级）**

```
# 6A-Workflow-for-Trae
# 适用：项目级规则，写进 Trae → Settings → Rules → Project Rules
# 激活口令：6A-start

阶段1【Align-对齐】
- 输出《REQ_项目名称.md》：需求背景、目标、验收标准、非功能指标、排除项
- 任何需求描述必须满足 INVEST 原则；验收标准必须"可测试、可量化"
- 需求未对齐，禁止进入下一阶段

阶段2【Architect-架构】
- 输出《DESIGN_项目名称.md》：系统上下文图（C4）、接口契约、技术栈、目录结构、时序图
- 先画后写：所有图用 Mermaid 源码呈现；无图不编码
- 对外接口先行：REST/GRPC 字段、错误码、鉴权规则一次写全

阶段3【Atomize-原子化】
- 任务粒度 ≤ 20 行代码或 ≤ 1 个函数；单任务必须 0.5 d 内完成
- 输出《TASK_序号_名称.md》：任务目标、输入输出、验收脚本（pytest/main 可直接跑）
- 复杂流程必须继续拆，直到"傻子也能一次写对"

阶段4【Approve-审批】
- 人工逐条 checklist：①验收脚本能否跑通 ②是否引用了设计文档 ③是否有性能/安全 TODO
- 审批通过后，在任务头部写入 APPROVED@yyyy-mm-dd-HH:MM 并 commit
- 未通过审批，AI 禁止生成生产代码

阶段5【Automate-自动化】
- AI 按 TASK 顺序编码；先写单元测试（pytest），测试红→绿→重构节奏
- 代码提交信息格式：<task-id>: <desc> (test=<cov>%, lint=pass)
- 测试覆盖率 < 80 % 或 lint 报错，自动阻塞提交

阶段6【Assess-评估】
- 生成《FINAL_项目名称.md》：SonarQube 扫描得分、测试覆盖率、遗留 TODO、性能基准
- 若 Sonar 阻塞级 bug > 0 或覆盖率 < 80 %，强制回滚到 Atomize 阶段
- 评估通过后打 tag：v{版本}-6A{日期}
```

**user_rules.md ── 5S 敏捷规则（个人级）**

```
# 5S-Agile-for-Trae
# 适用：个人侧规则，写进 Trae → Settings → Rules → User Rules
# 目标：让开发者成为"AI 驯兽师"，杜绝跳步与返工

1S - 文档（Document）
- "先写文档后写代码"是铁律；任何代码文件头部必须带 3 行注释：作者、创建/修改时间、对应 TASK-ID
- 目录说明 README 必须同步更新，否则 AI 拒绝继续编码

2S - 流程（Sequence）
- 严格执行"需求→设计→任务拆分→测试→代码"顺序；禁止反向跳转
- 每日启动 Trae 时，先输入"5S-check"，AI 自动校验昨日产出是否合规

3S - 问题（Solution）
- 遇到报错第一步：贴官方文档链接 + 错误日志；禁止直接问"为什么错了"
- 搜索引擎 / 官方 Doc 未读完，不允许让 AI 直接给答案

4S - 约束（Constraint）——三大"绝不允许"
  a. 绝不允许项目延期：提前 3 d 识别风险，延期必须同步更新甘特图 & 通知干系人
  b. 绝不允许超出范围：新增功能须先改《REQ》并评估影响，未经审批不加
  c. 绝不允许低级错误：编译报错、测试 fail、文档不一致，零容忍立即回滚

5S - 环境（Standardized-Env）
- 全团队统一：Win11 + Python3.11 + Node20；包管理锁文件（requirements-lock.txt / package-lock.json）强制提交
- IDE 插件版本锁定：Prettier@2.8.0、ruff@0.6；差异提交前自动 format，不通过禁止 push
- 输出规范：函数注释必须含参数类型、异常、返回值结构
```

> 效果数据（`[2025-09-28 22:27] 庄子村`，来源同篇文章，2025-08）：电商优惠券系统实测——**返工率 40% → 5%，单人日功能点 3 → 8，Sonar 缺陷 20/千行 → 3/千行，提前 5 天零 BUG 上线**。

### 1.4.2 md 规则文件：把"领域知识"沉淀成可拖拽的文件

群里最实用的一招，是把零散要求写进 `.md` 规则文件，需要时"拖给"对应智能体：

- **翻译风格化**（`[2025-11-17 20:21]` FYF）：「你可以把一些特定翻译放到 md 里，然后告诉他好坏例子，慢慢调整 ai 翻译的风格化」。
- **同类场景用示例提准确率**（`[2025-11-18 12:17]` 冬沐）：「提示词中贴示例确实很好用，我之前写一个 AI review 的功能，贴上示例后，准确率提升了很多」。
- **代码清理规则用 md 承载**（`[2025-11-18 10:40]` FYF）：「都不用智能体，整理一个 md 规则，要得时候后拖到整理代码的智能体上，会一并处理的」。

### 1.4.3 上下文遗忘 / 丢失的应对

**先认清问题**：`[2026-04-11]` 用户107122——「ai 模型在大框架上经常不看文档，上下文不够用的时候就会只看你这次的提示词了，然后哪哪对不上了」；`[2025-11-19]` 刘金良——「别太相信模型，提示语与上下文还是要好好搞搞」。

### 1.5.6 高质量长提示词 / 规则原文（可直接抄）

**Skill 创作规范提示词**（`[2026-06-10 11:39-11:40]` AAG：「skillcreate 的这套提示词，特别好用」「我直接扔规则里了」）：

> ## Writing Style Requirements
>
> ### Imperative/Infinitive Form
> Write using verb-first instructions, not second person:
> **Correct (imperative):**
> ```
> To create a hook, define the event type.
> Configure the MCP server with authentication.
> Validate settings before use.
> ```
> **Incorrect (second person):**
> ```
> You should create a hook by defining the event type.
> You need to configure the MCP server.
> You must validate settings before use.
> ```
>
> ### Third-Person in Description
> The frontmatter description must use third person:
> **Correct:**
> ```yaml
> description: This skill should be used when the user asks to "create X", "configure Y"...
> ```
> **Incorrect:**
> ```yaml
> description: Use this skill when you want to create X...
> description: Load this skill when user asks...
> ```
>
> ### Objective, Instructional Language
> Focus on what to do, not who should do it:
> **Correct:**
> ```
> Parse the frontmatter using sed.
> Extract fields with grep.
> Validate values before use.
> ```
> **Incorrect:**
> ```
> You can parse the frontmatter...
> Claude should extract fields...
> The user might validate values...
> ```

> 月亮，我会先开始想 elements: 光，月亮，反射，星星，坑。然后你尝试给每一个画一个简洁的图形，然后考虑如何合并几个点子

## 1.6 高效工作流范式总结

### 1.6.1 核心范式："贵模型搭架 + 便宜模型干活 + 强模型审核"
