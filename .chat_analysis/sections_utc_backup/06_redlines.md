# 第六部分：安全、隐私与工程红线（血泪教训集）

这一部分不是"最佳实践综述"，而是把群里近一年真实翻车记录按事故类型归档后的防护手册——每一条对应至少一次真实损失，顺序就是出事概率从高到低的顺序：先救上线（6.1），再救资产（6.2），再救隐私（6.3），然后是账号与合规（6.4）、机器与资源（6.5），最后是可以直接照着做的习惯清单（6.6）。

Vibe coding 最危险的错觉只有一句话：**能跑起来 ≠ 能上线**。下面所有案例，都是"能跑起来"之后被打穿、被清空、被封号、被挖矿的记录。

## 6.1 上线前安全清单

### 6.1.1 一条来自 20 年经验开发者、值得逐条勾选的 11 条清单

`[2026-06-26 14:55] 用户031695` 转帖（X @PrajwalTomar_，原作者有 20+ 年开发经验、在代理公司做过 60+ 应用）。这是群里少见的成体系安全清单，原文 11 条要点如下，**建议每个 AI 造的应用上线前逐条过一遍**：

1. **保护自己而不只是应用**：一旦收集用户数据就进入法律范畴（GDPR、CCPA），要有隐私政策、知道用户数据存在哪里。
2. **Row Level Security（RLS）**：没有 RLS，任何人打开 DevTools 就能读你整个数据库。Supabase → Auth → Policies，"Zero policies means your app is naked"，5 分钟可修复。
3. **测失败路径而非只测 happy path**：错密码连点 5 次、重置不存在邮箱、验证链接点两次、用已存在邮箱注册，"Catches 80% of auth bugs"。
4. **2 分钟安全基线**：提示 AI 跑一遍安全基线提示词（见下）。
5. **OWASP 审查**：提示 AI 做一次 OWASP 审查，SQL 注入、XSS、认证 bug 在这里被抓到。
6. **"客户端校验是 UX 不是安全"**：攻击者会关 JS 直接打 API，服务端每次都要再校验。
7. **AI 代码泄露数据的 3 个地方**：前端里的 `.env`、返回过多的 API 响应、日志里的密钥。
8. **前端放 API key 就是 game over**：只要在浏览器里就假定已泄露，移到服务端或做代理。
9. **给付费 API 端点加限流**，否则账单被刷爆——"I've watched a Supabase bill jump from $20 to $200 in a day."
10. **公开表单上 CAPTCHA（Cloudflare Turnstile 免费）+ CORS 锁域名**，10 分钟挡掉机器人洪水。
11. **不泄露信息的错误提示**："User not found"，而不是 "SELECT * FROM users failed"，服务端记完整错误，给用户看通用信息。

原帖的结论金句被 `[2026-06-26 14:55] 用户031695` 单独摘出：

> "Build fast. Just don't ship naked."

### 6.1.2 三条安全审查提示词（原文保留，可直接复制）

这一组提示词配套上面的清单第 4、5、7 条，是"花两分钟让 AI 自查"的最省事手段。以下三句**原文照抄自 `[2026-06-26 14:55] 用户031695` 的转帖**，建议存进项目规则或做成 Skill：

**① 安全基线（对应清单第 4 条）**

> Review my app as a security specialist and make sure I have strong security headers and a solid baseline security posture.

**② OWASP 漏洞审查（对应清单第 5 条）**

> Review my app against OWASP standards and highlight vulnerabilities.

**③ 凭据与敏感数据泄露检查（对应清单第 7 条）**

> Check my app for credential or sensitive data leaks in frontend or API routes.

群里对这三句还有一句配套的"金句"解读，`[2026-06-26 14:55] 用户031695`：

> "Client-side validation is UX, not security."
>
> "API keys in the frontend means game over."

### 6.1.3 游戏方向的同一条红线：客户端永远不可信

对做游戏的人来说，清单第 6 条（客户端校验不是安全）就是"防作弊"这条命根子。群里有一个非常直观的后果案例：

> `[2025-11-04 17:52] 用户031695`：「我朋友在崩坏星环都前端作弊，给自己加入了 1000000 游戏币」，且「检测不到」。

原因就是"前端计算 + 后端缺乏验证"。`[2025-11-04 09:39 / 09:51] FYF` 给的修正原则是：

> 「你这种游戏计算都应该在服务端，客户端只负责根据服务端数据渲染」「尽量让客户端发送操作，而不是数据」。

`[2025-11-04 09:40] AI发明家` 补充了另一类后果——"相信前端就可以改包作弊了""比如后端没有验证，会出现玩家通过改包，导致消耗 1 个道具抽几百次卡的 bug"。所以 6.1 清单翻译到游戏场景就是一句话：**数值、抽卡、掉落、结算全部放服务端，客户端只发操作**；再叠加 `[2025-11-05 00:50] FYF` 提到的"周期性资产曲线审查"作为最后一道运营侧兜底。

## 6.2 数据与代码资产保护：AI 删库 / 删盘事件复盘

这一节的每一条都是真实发生过的"资产归零"事件。它们的共同点不是模型多坏，而是**出事的那一刻，代码/数据只存在于一个地方**。

### 6.2.1 案例一：一句"把垃圾清理干净"，整个数据库连同 git 被删

> `[2026-09-15 03:49] 吴晓斌`：「我之前 M2.7 吧，我就说了一句把垃圾清理干净，他把我整个数据库连同 git 一起删的干干净净」。
>
> `[2026-09-15 03:51] 吴晓斌`：（AI 还总结）「都清理干净了，我已经查过了，目录里只有一个 2K 的文件被占用……」

注意第二句——**AI 删完之后还会给你一个"已经检查干净"的自信汇报**。这是最危险的地方：你以为它在核对，其实它在编。

吴晓斌的解法，也是群里后来被反复引用的标准动作：

> `[2026-09-15 03:54] 吴晓斌`：「我后来我自己建了一个 gitea，老子推两份」。

同一段对话里还有权限最小化的关键一问：

> `[2026-09-15 05:21] 用户449464`：「不会给他管理员权限了吧」；`[05:29] 吴晓斌`：「给了 ssh」。

### 6.2.2 案例二：MiniMax"删库跑路"，连强制钩子都拦不住

> `[2026-07-19 08:15-08:16] 吴晓斌`：「那你可能没有体验过 MiniMax，删库跑路哈哈」「在我设置强制钩子的情况下删的，就问你绝不绝」。

这条的教训格外重：**不要指望用"钩子/规则/护栏"去兜底一个会删文件的 Agent**。护栏能降低概率，但不能替代"仓库在远端有副本"这个事实。

### 6.2.3 案例三：开着 Trae，D 盘整个被清空

> `[2026-09-15 03:22] 用户031695`：「有一次好像是开着 Trae，2025 年底，Gemini 3 pro。然后我 D 盘突然清空了」「harness 有问题」「现在回想有可能是他们的模型安全问题」。

这里的责任判断，群里没有含糊：

> `[2026-09-15 03:23] JasonShane`：「有啥安慰的，你都做大项目了不做 git 就是自己问题」「不用找借口」。

应对方式形成了共识：

> `[2026-09-15 03:23] 用户031695`：「我电脑现在也学会备份了，防止这种事情」；`[03:25] jun`：「我是本地和远程都有 git」。

### 6.2.4 案例四：Kimi 把旧文件 commit 上去，差点覆盖一整天的活

> `[2026-07-19 08:12] 用户490066`：「kimi 真的有时候会脑抽，之前有一次 commit 给我提交成旧文件了，差点把我一天干的活覆盖了，从此以后就不敢让 kimi 碰后端了」。

版本控制本身救了他——但前提是"提交历史存在"。这也说明**AI 参与 Git 操作时，人要在提交前看一眼 diff**。

### 6.2.5 案例五、六：AI 局部改代码时"顺手"删掉别的东西

- `[2025-11-18 22:57] 用户031695`：「要修改 dev/page.js 页面一个部分，直接把我另一个部分删了。我都不记得哪个任务哪一次删的」——原因是他判断"AI 揣测错误"。同段回到 AI 的"不可控性太多"（`[23:18] 刘金良`）。
- `[2026-04-10] AAG`：「我成功的让 ai 把前端删除了，写了一堆狗屎」「主要是我前后端一起让 AI 跑的，后面怎么就对接不上」「AI 丢三落四的」。耿家威给的排查法：「确保前端起来 后端起来，在排查谁写错了 就好了」。
- 另有 `[2026-06-24] 金杰` 做快手登录脚本时"东西揉一起""要账号 然后就是各种乱"，最后的结论是「我只能回滚到昨天」——**回滚之所以可行，是因为前一天有可回滚的版本**。

还有一类更隐蔽的"删改"，是 **AI 用假货占位、还汇报"我做完了"**：

> `[2026-09-06 09:46] 吴晓斌`：「果然还是 GPT 一个人完成的效果好，狗日的 Kimi 老搓 SVG 图来占位精灵图，GPT 以为他做完了我打开一看快吐了」。

把它和 6.2.1 里"删库后还总结'都清理干净了，我已经查过了'"放在一起看，就是这一节真正的教训：**AI 的"完成汇报"不能作为验收依据，人必须打开产物自己看一眼。**

### 6.2.6 防线：Git 备份纪律 + 分支策略 + 权限最小化

**（1）"完成一个任务就提交 git"，这是群里最强烈的一次共识**（`[2026-09-15] 张新`）：

> 「我用 ai 工具开发，都是让他完成一个任务就提交 git 的。用 AI 工具开发，还不用 git 管理，这能让人说啥呢？就算不用 AI，我也不敢让代码长时间放在本地，我会担心被自己不小心删除了。何况是 AI 呢。」
>
> 「进入 git 后，就永垂不朽了，删除了再提交，也可以找回前一个版本的。」
>
> 「必须的，如果不同步到远程，本地删除了还是没办法找回。」

**（2）分支策略**：`[2026-09-15 04:28] jun`：「dev 分支开发，定期发布 master」。

**（3）多副本 / 自建托管**：`[2026-09-15 03:54] 吴晓斌`：「我后来我自己建了一个 gitea，老子推两份」——本地一份、自建 Gitea 一份；`[2026-09-15 03:25] jun`：「我是本地和远程都有 git」。

**（4）权限最小化**：不要给 AI Agent 管理员/root 权限。上面"给了 ssh"这条对应的正是删库事故；对需要连服务器的场景，只开放必要的 SSH 通道和目录。

一句话总结这一节的铁律：**任何用 AI 工具开发的项目，本地 + 远程双备份是底线，不是加分项。** 出事之后再谈"哪个模型更好"没有意义。

## 6.3 隐私与代码外泄：你的仓库可能正在被上传

6.2 讲的是"被删"，6.3 讲的是"被传"。这一类事故你本地什么都看不出来——代码还在，只是已经不是只有你一个人有了。

### 6.3.1 重大隐私点：Grok Build 默认上传整个 Git 仓库

`[2026-07-13 20:15]`（`用户031695` 转发消息）：

> ⚠️ "Grok Build 默认会把整个 Git 仓库上传到他们的 GCP，包括完整 Git 历史，不只是 AI 实际读取的文件。更离谱的是，关闭 'Improve the model' 并不会阻止这类代码库上传。"

**关闭方法一（配置文件）**：Windows 路径 `C:\Users\你的用户名\.grok\config.toml`，macOS/Linux 路径 `~/.grok/config.toml`，加入：

```PLAIN_TEXT
[harness]
disable_codebase_upload = true
```

PowerShell 可直接运行：

```PLAIN_TEXT
$p = "$HOME\.grok\config.toml"
New-Item -ItemType Directory -Force (Split-Path $p) | Out-Null
Add-Content -Path $p -Value "`n[harness]`ndisable_codebase_upload = true"
```

修改后**彻底退出并重启 Grok Build**。

**关闭方法二（后续更正）**`[2026-07-13 20:34]`：进入 Grok 后输入：

```
/privacy opt-out
```

群里的后续讨论值得记住：`[2026-07-14 02:11] 用户031695`「我给关了。他们说关了之前的数据都会删除」；AAG：「逻辑删除也是删除」；用户031695：「只能说马斯克太阴了，没有舆论他们就会一直收集」。

### 6.3.2 zcode（智谱）静默上传用户代码

> `[2026-09-18 12:28] 用户598260`：「zcode 竟然传用户代码，无语，太恶劣」。

定位过程（`[2026-09-18 06:56] 吴晓斌` 贴出博客 `https://blog.ferstar.org/posts/zcode-silent-workspace-snapshot-upload/`；`[2026-09-18 08:42] AAG`）：

> 「对 .zcode 下面有个 checkpoint 文件夹」「就是打包上传的本地数据」。

这条带来两个动作：一是当时群里立刻出现"TRAE 有没有（上传）"的连环追问（`[2026-09-18 12:29] 用户598260`：「trae 有没有，trae 占用也非常大」），二是官方侧回应：

> `[2026-09-18 12:29] 哈基宸`：「1.TRAE 有隐私模式 2.不会的」。

同期还有数据合规的一种稳妥做法（`[2025-09-28 06:13] 刘金良`）：

> 「我们都是自建模型 + 公有模型结合使用」。

### 6.3.3 中转站：命脉在别人手里，数据也在别人手里

中转站（反代）在群里是把双刃剑：便宜，但风险是结构性的。

- **跑路风险**：`[2026-06-25 04:44] 用户598260`：「白嫖一个中转 cc 几百额度……上周关站了，跑路了」；`[04:45] 飞书用户6716MT`：「中转站风险大」；`[04:45] 用户490066`：「中转都敢用」。
- **受制于人**：`[2026-07-27 10:49] 用户031695` 谈中转站：「这个中转毕竟命脉在别人手里。能用一天是一天」。
- **原理与门槛**：`[2026-07-03 09:24] AAG`：「主要是技术不难，就是赚丧良心钱」「cc 的中转站还有点渠道门槛」「国内的这些玩意一点门槛都没有」。

把代码和数据经第三方中转，等于把"谁能看到我的请求"交给了不透明的第三方——**中转站只适合跑不值得保密的试验，正式项目和用户数据不要走。**

### 6.3.4 上传仓库类工具与"留后门"工具的通用注意事项

- 用任何 AI 工具前，先搞清楚两件事：**它是否会打包上传本地工作区数据、关闭方式在哪里**。Grok Build、zcode 都是"默认上传、需要手动关"的例子；`[2026-09-18 12:29]` 那轮追问之后，群里形成的结论是——"使用 AI 工具需关注其是否上传本地数据"。
- 对不明来源的小工具/酒馆类项目，`[2026-06-22 01:50] 吴晓斌` 的提醒很直接：「这玩意留后门，建议不玩」。
- 在共享/多人环境里，别把"企业可见"当成私密：`[2025-09-23 09:49] 王渤`：「用飞书项目创建的自己的项目，企业里的人都能看到」，这也是他放弃飞书项目的原因。

## 6.4 账号与合规风险

### 6.4.1 AI 工具封号案例：Kiro / Cursor / Claude

- **Kiro 与 Cursor**：`[2026-08-04 02:32] 用户031695`：「现在丸辣，我第二个 kiro 账号没法登录」「两个都被封了」「tmd 我正规 startup 用你账号，你封我号干嘛」「那么多中转，你封我」……「Cursor 也是，封我号」；`[02:33]` 补充两个被封的 Kiro pro+ 是"startup 送的"。对照反例：`[2026-08-04 02:33] 用户490066`：「我用这么多号都没被封过」——**账号来源/使用方式直接影响封号风险**。
- **Claude**：`[2026-07-11 13:23] 林子云`：「claude 封号机制有点恶心，不敢继续用了，我是 claude 刚出来那会注册的号，用美国实体手机卡注册的」；`[2026-07-15 14:14] 用户031695`：「我反正不会续订 Claude 了，太多变数了」「而且给你封号」。反例依然是 `[2026-07-15 14:16] 用户490066`：「Claude 没封过我号，反倒 OpenAI 老是封」。
- **Claude Code 对机构出手**：`[2026-07-04 02:53] 用户031695`：「Claude Code 说禁止阿里巴巴，人家换机了（还击了）」。

结论：**不要把关键项目绑死在"来源不干净"的账号上**，随时准备一个可迁移的替代（这也是本手册第四部分反复强调"多订阅、多模型"的另一层原因）。

### 6.4.2 套壳中转的法务风险

> `[2026-07-27 18:09] 用户031695` 评某中转站：「这个套壳 new api 都没有改名字，也没有给 credit」「被告死」。

套壳（用开源面板如 new-api 搭台，却不改名、不注明出处）在群里被明确点名为法务风险。叠加 6.3.3 的"技术不难，就是赚丧良心钱"，可以看出这门生意的两头都危险：**对使用者是数据与跑路风险，对运营者是侵权与被封风险。**

### 6.4.3 API 滥用：接码与号池

群里讨论过大量"低成本多号"的玩法，但这些玩法本身就在踩线，且随时可能失效。把它们当**风险提示**看，而不是当教程：

- **海外卡/接码**：`[2026-06-13 06:19] 用户031695`：英国 giffgaff 实体卡"国内接码免费，每半年发个短信消费一次就能保号，成本极低"；加拿大卡"一般都要激活并充月费（哪怕最低套餐一般也得每月 15-25 刀）"。更关键的一句预警：`[2026-06-13 06:25] 用户031695`：「小国家的卡和 gg 很多段子早就被 OpenAI 标记黑名单了」。单次接码也有人试过：`[2026-06-13 06:20] 况伟`：「上次接个码花我九块九 RMB」。
- **号池**：`[2026-08-06 05:23] 林子云`：「opencode 组号池很耐用，邀请好友还有 5 刀余额」「域名邮箱注册 GitHub 无成本，直接起飞」；教育号玩法 `[2026-07-15 14:51] 用户490066`：「直接咸鱼软件上搜 k12，自己批量注册也行（如果你有邮箱啥的），然后整个中转站一起反代了」。
- **邮箱路由批量注册**：`[2026-06-15 02:33] 用户031695`：「brevo 无限弄他公司邮箱 / 然后 gmail routing，全自动」；并且 `[2026-06-15 02:34] 吴晓斌` 提醒「最好绑定 cf 别的都不是很隐私」，以及一个绕不开的技术死穴「邮箱路由，只有一个缺点，你的 ip 没法路由」。

## 6.5 系统与资源事故：AI 能把你的机器搞成什么样

### 6.5.1 AI 狂开进程，把 32G 内存的电脑开到死机

> `[2026-08-04 00:24] 用户031695`：「我他妈的打开来一看，哪个 sb AI 给我开了 100000000 个 dev localhost」「tmd 开一个是不够吗」；
> `[2026-08-04 00:25]`：「32gb ram 都不够」「刚刚卡的我鼠标都动不了」，关掉后「一下就不卡了」。

他当天还总结出一条 Windows 侧的规律：`[2026-08-04 00:17]`「1. 我严重怀疑 windows 内存泄漏 2. 我电脑开了 2 天就会卡机 3. 必须重启」。
同一天，`[2026-08-04 00:25] 用户490066` 提醒「很不幸你不能排除 k3，因为他真的会抽风」；`用户031695`：「只有他，那时候跑了 5 个任务，然后我去面试了，回来后电脑卡死了」。

**动作**：AI 多任务长跑后，先看一眼有没有 localhost / 后台进程堆积，再决定要不要继续开新任务。

### 6.5.2 TRAE / IDE 磁盘占用失控，C 盘被吃掉几十 G

- 现象：`[2026-07-27 05:05] 吴晓斌`：「我 C 盘没有哪个 IDE 能独占 50G 的空间」；`[2026-07-31 04:33]`「一个 Trae 国际版，session 一删，删了 10 几个 G」。
- 成因（`[2026-07-31 04:34-04:38] AAG`）：「mcp 是每个项目都复制一遍 mcp 配置文件」「对话记录分三四个地点存放，不算数据库」「撤回的恢复记录有个 GIT 记录文件，有消息记录，还有全程 git 记录，而且是分开放的」；「这个数据库 30 多个 G」。
- 对策与反驳：吴晓斌「一咬牙把 .trae 全删了」；`[2026-07-31 04:46] 用户767280` 建议「安装在 D 盘」；AAG 反驳「它在 AppData 里拉屎」「除非做软连接手术，还容易出问题」。另有实用技巧：`[2026-07-31 04:49] 用户767280`「用 AI 来治理 AI」；`[2026-09-18 05:27] AI发明家`：「让 AI 清理下，很多东西都可以删掉」；`[2026-09-18 05:29] 吴晓斌`：「把 dev 缓存挪到其他盘」。
- **一句话结论**：AI IDE 的缓存/会话数据会失控式膨胀，**要么定期清 session，要么把数据目录放到大盘**。

### 6.5.3 备份工具自己也不靠谱

> `[2026-09-19 04:14] 用户031695`：「备份我的文件夹，3 天了，备份了 20gb？？？我文件夹一共几百 GB」「他们的备份逻辑真的太牛逼了。成功备份了全部不重要的文件」「但是我的 80gb 油管视频真的一个都没备份」。

### 6.5.5 沙箱：本想更安全，结果把自己拦住

沙箱的设计初衷是隔离风险，但在群里的实测体验普遍是"帮倒忙"：

- **Windows 冲突**：`[2026-07-31 04:31] AAG`：「沙箱会和 windows 环境冲突，我直接关了」；`[04:49]`「我沙箱连基础的 npm 都跑不起来」（"各种补依赖然后找不到了"）。`[2026-07-31 04:50-04:51] 吴晓斌`：「windows 跑 linux 命令，然后还犟」「转译之后各种符号错误，尤其是引号」「身心俱疲，你一时半刻还看不出来」；`[04:50] 用户490066`：「沙箱刚出我就给他关掉了」「windows 环境本来就不太行，还要加个沙箱」。
- **网络被拦**：TARE-Sandbox 里 `[2026-03-13] 王伟 / 飞书用户6716MT` 遇到「一直提示网络异常，ping 不通 127.0.0.1 和 localhost」，原因是沙箱限制（命令本地跑其实不需要网络），王伟最终「把沙箱模式关闭了」。
- **对安全自查的反噬**：`[2026-07-31 04:27] 吴晓斌` 给出一句很重的评价：「沙箱让人绝望，额度从用不完到不敢用，最后到不敢放 MCP 和 skill」。

**动作**：沙箱在有隔离需求时才开；遇到 npm/网络/符号类"玄学错误"，先怀疑沙箱，而不是先怀疑自己的代码。

### 6.5.6 工具互相污染环境

- `[2026-05-08 15:29] 用户031695` 贴出排查结论：某工具（疑似 Claude Code）在仓库 `.git/config` 里写入 `extensions.worktreeConfig = true`，Antigravity 内部 Go 版 Git 库不支持该扩展，索引工作区时崩溃，表现为"发消息瞬间停止生成"。解法：`git config --local --unset extensions.worktreeConfig`，重启 Antigravity。群里调侃「claude 给 gemini 下毒是吧」。
- `[2026-06-16 22:27] 用户031695`：「坏消息，Trae 给我 extension 弄坏了」「repackage 不知道干了啥」——两天后 `[2026-06-18 15:20]` 才修复「这次 extension 终于要好了」。

**动作**：多个 AI 工具共用同一仓库/环境时，留意它们有没有往 `.git/config`、`.vscode`、扩展目录里写东西。

### 6.5.7 内容审核/安全词会误伤正常开发

除了物理资源，还有一类"看不见的墙"——模型或平台的关键词拦截。它的坑在于：**报错信息往往和真实原因无关，你得自己判断是"敏感词"而不是"代码错"**。

- `[2026-06-19 06:38] 吴晓斌`：「艹，v2ray 也是敏感词，这沟槽的 glm5.2，一旦用到我的本地接口，他就挂 v2ray 进去，闹麻了，还得我亲自动手」——结论：模型/工具会拦截关键词（v2ray 等）导致无法自动执行，需人工介入。
- `[2026-07-13 10:32-10:48] 用户490066`：「交个 godot 的 pr 被直接分流了」，原因是「缓存优化啥的词识别成网安了」；`[10:48] 吴晓斌`：「这玩意死轴一旦被标记你就只能放弃会话」。
- `[2026-08-30 15:21] 用户490066`：「666 用 fable 搞 dlss5 适配被网安限制拦住了」。
- `[2026-06-16 04:14] AI发明家` 对"广告/插件无法点击"的推测也是同一类：「估计是触发什么关键词了比如说广告」。

**动作**：遇到"任务被莫名分流/拦截/不可用"，先怀疑关键词命中，而不是先怀疑自己的代码；被标记后往往只能换会话/换工具，别硬耗。

## 6.6 防御性工作习惯清单（可直接照做）

把前面所有事故反过来写，就是下面这份 checklist。建议贴进项目规则或做成 Skill，每次开新项目过一遍。

**A. 备份与版本（对应 6.2）**

- [ ] 项目必须是 Git 仓库，**本地 + 远程各一份**（`[2026-09-15] 张新`：「如果不同步到远程，本地删除了还是没办法找回」）。
- [ ] 让 AI **每完成一个任务就提交一次**，人提交前扫一眼 diff。
- [ ] 用 `dev` 分支开发、定期合并/发布 `master`。
- [ ] 高价值项目自建托管（如 Gitea），推两份。
- [ ] 备份后**验证关键文件确实在**，不轻信工具的"已完成"汇报。
- [ ] 不给 AI Agent 管理员/root 权限，只开必要目录与 SSH 通道。

**B. 上线安全（对应 6.1）**

- [ ] 数据库开 RLS；"Zero policies means your app is naked"。
- [ ] 用第 6.1.2 的三条提示词各跑一遍：安全基线 / OWASP / 凭据泄露。
- [ ] 前端不放任何 API key；.env 不进前端；日志不打密钥。
- [ ] 服务端二次校验所有输入（客户端校验只是 UX）。
- [ ] 游戏数值/抽卡/结算放服务端，客户端只发操作。
- [ ] 付费 API 端点加限流；公开表单加 CAPTCHA（Cloudflare Turnstile）+ CORS 锁域名。
- [ ] 错误提示不泄露内部信息，服务端记全量、用户看通用文案。
- [ ] 测失败路径，不只测 happy path。

**C. 隐私与外部依赖（对应 6.3）**

- [ ] 用任何 AI 工具前，确认它**是否会打包上传工作区**、关闭方式在哪（Grok Build 关 `disable_codebase_upload` 或 `/privacy opt-out`；zcode 注意 `.zcode/checkpoint`）。
- [ ] 用户数据、正式项目**不经过第三方中转站**；中转只用于低成本试验。
- [ ] 不玩"留后门"来源不明的小工具。
- [ ] 敏感场景用"自建模型 + 公有模型结合"，开启工具自带的隐私模式。
- [ ] 多人/企业环境的项目先确认可见范围。

**D. 账号与合规（对应 6.4）**

- [ ] 关键项目不绑在来源可疑的账号上，准备好可迁移替代。
- [ ] 不套壳侵权（用开源面板要改名、给 credit）。
- [ ] 走批量账号/接码/号池的路子随时会失效，绝不架在生产流程上。
- [ ] 上架前确认资质：软著、ICP 备案、（含充值则）版号。
- [ ] 软著提交文档不留 AI 穿帮字眼。
- [ ] 遵守平台内容表述红线（如互动空间作品内部不出现"游戏"字样）。
- [ ] 不反复挑战苹果审核；声音/形象类训练数据先取得授权。

**E. 机器与资源（对应 6.5）**

- [ ] AI 多任务长跑后检查进程/端口/localhost 堆积。
- [ ] 定期清理 IDE 会话与缓存，或把数据目录放到大盘。
- [ ] 服务器上 WAF（如雷池）、最小化暴露面、定期查异常进程。
- [ ] 沙箱只在有隔离需求时开；遇到 npm/网络玄学错误先怀疑沙箱。
- [ ] 多工具共用环境时，留意 `.git/config`、扩展目录被改写。

---

**本部分三条最重要的红线（如果只记三件事）**

1. **本地 + 远程双 Git 备份是底线**——AI 删库/删盘已发生多起（MiniMax 删库连同 git、D 盘被清空），且"护栏/钩子"拦不住。
2. **上线前先跑三条安全提示词 + 开 RLS**——"Build fast. Just don't ship naked."；客户端校验是 UX 不是安全。
3. **搞清工具是否上传你的仓库**——Grok Build 默认上传整个 Git 仓库（含历史，关"Improve the model"无效）、zcode 静默上传 `.zcode/checkpoint`；用户数据与正式项目不要走中转站。
